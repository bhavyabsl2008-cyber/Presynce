# Architecture

## Stack

Next.js (App Router) + TypeScript + Tailwind CSS v4 + Motion (formerly
Framer Motion) + Firebase/Firestore + Vercel hosting.

Primitives are hand-written in the shadcn/ui convention (cva + Tailwind),
not generated by the shadcn CLI — the CLI needs an interactive prompt
(Base UI vs React Aria vs Radix) and a registry fetch that isn't always
reachable from the build environment. Functionally equivalent; revisit
if a real preference on the underlying primitives library emerges.

## Layer boundaries (strict)

```
/domain            pure functions, zero framework imports, unit-testable
/services           the ONLY place allowed to import Firebase
/hooks               the ONLY seam between components and domain+services
/components/ui       dumb, reusable primitives (Button, Card, ...)
/components/features actual product UI, composed from /components/ui
```

Why this exists: v1 had no such boundary, and its worst bugs (see
engineering-manifesto.md) came from domain logic tangled into UI code
where it couldn't be tested or trusted in isolation. `/domain` is the
layer that catches real bugs — every attendance calculation, threshold
check, and recovery-math function lives there and nowhere else.

**Current reality vs. the diagram above:** `/domain` and
`/components/ui` and `/components/features` exist and are populated
(see "What's actually implemented" below). `/services` and `/hooks` do
**not exist yet** — there's no Firebase integration and no data-fetching
seam built. The boundary is a rule for when those layers get built, not
a claim that they currently exist. Don't assume there's existing
service/hook code to inspect; there isn't.

Explicitly rejected: Redux, a general API abstraction layer, and a
multi-university abstraction layer. v1's real problems never came from
having too little architecture — they came from guessed domain facts and
duplicated logic. Don't add structure that isn't solving an observed
problem.

## What's actually implemented (as of this handoff)

Everything below exists and compiles (`npx tsc --noEmit` clean,
`npx eslint src` clean) as of the latest milestone. Nothing in this
section is a proposal.

**`/domain`**
- `attendance.ts` — `computeAttendanceReading(snapshot)`: pure function
  taking `{ attended, held, threshold }`, returning percentage, status
  (safe/warn/danger), safe skips remaining, and classes needed to
  recover. This is the single source every attendance stat traces back
  to.
- `priority.ts` — `scoreSubjectPriority`, `rankSubjectsByPriority`,
  `selectHeroSubject`. A weighted scoring model (plain `PriorityWeights`
  object, swappable without touching UI) that determines which subject
  becomes the dashboard's "hero" — factors are distance below
  threshold, scarcity of remaining safe skips, cost to recover, classes
  scheduled soon, and an "unrecoverable" heuristic (recovery cost
  exceeds what's actually scheduled). This is NOT "lowest percentage
  wins" — a subject with a higher percentage but an implausible recovery
  path can outrank one with a lower percentage but real upcoming
  classes to recover with.

**`/components/ui`**
- `button.tsx` — cva-based variants (primary/secondary/ghost/
  destructive), sizes (sm/md/lg), built on `motion.button` with a
  `whileTap` press interaction. Not a native `<button>` — a motion
  component with button semantics.
- `card.tsx` — base card plus an `elevated` boolean variant using the
  `--shadow-raised` token (defined since Milestone 1, unused until the
  craftsmanship pass added the `elevated` prop).

**`/components/features/dashboard`**
- `runway-bar.tsx` — the signature attendance visual. Not a progress
  ring. Shows percentage, a fill bar with a threshold marker, and an
  always-present action line. Has a `size="hero" | "compact"` prop —
  hero size uses large split-number typography (big integer, smaller
  decimal) with a spring count-up animation; compact is the smaller,
  static-number version.
- `subject-row.tsx` — the dense rail list item. Status dot, name,
  action text, percentage, hover-revealed chevron. Uses Motion's
  `layout` prop so re-sorting animates rather than snaps.
- `dashboard-hero-rail.tsx` — the current dashboard composition:
  priority-ranked hero (via `selectHeroSubject`) in full detail, the
  rest as compact rows, then a separate "Log today" action card. Hero
  is wrapped in `AnimatePresence` keyed by subject name so a hero change
  crossfades.
- `dashboard-grid.tsx` — the original Milestone 1 equal-weight-card
  layout, kept unmodified as a one-line revert path. See
  `rejected-directions.md`.

**`/components/features/nav`**
- `rail-nav.tsx` (desktop, left rail) / `tab-bar.tsx` (mobile, bottom
  tabs) — both use `usePathname` for real active-route detection and a
  `layoutId`-based sliding active indicator (Motion). `nav-items.ts` is
  the single shared route list both read from.
- `app-shell.tsx` — composes `RailNav` + page content + `TabBar`.

**`/lib`**
- `motion.ts` — the shared motion vocabulary: `EASE_CALM`,
  `DURATION.fast/base/slow`, `TRANSITION_CALM`. Every animated thing in
  the codebase imports from here rather than inventing local values.
- `cn.ts` — `clsx` + `tailwind-merge` className helper.

**`app/page.tsx`** — the entry point. Holds a `DASHBOARD_LAYOUT`
constant (`"grid" | "hero-rail"`) that switches between
`dashboard-grid.tsx` and `dashboard-hero-rail.tsx` — the revert
mechanism mentioned above. Currently set to `"hero-rail"`. Subject data
is currently hardcoded test data in this file, not fetched from
anywhere — there is no data layer yet.

**What does not exist yet:** `/services`, `/hooks`, any Firebase
integration, any test suite (v1 has 42 passing tests; v2 has none —
see `open-questions.md`), any dark-mode toggle (tokens exist, nothing
applies them), `/analytics` and `/profile` pages (nav links point at
routes with no `page.tsx` behind them — this is intentional; those
screens were explicitly kept out of scope until built for real rather
than designed hypothetically).

## Data & auth

Auth is required from day one — no anonymous/local-only mode. This is a
deliberate trade: v2 gives up the "no login" pitch and offline-first
behavior in exchange for one source of truth per user.

**Open, unresolved:** v1's existing localStorage data needs a real
migration/claim path when a returning user signs in for the first time —
not silent data loss. This must be designed before the auth flow ships,
not after.

## Deploy workflow

Development happens in a sandbox that cannot push to GitHub directly.
Workflow: build/edit in sandbox → produce git bundle files → fetch, merge,
and push from the real machine. Real download path is
`C:\Bhavya\Presynce\`, not the Downloads folder (this caused confusion
once — always extract/place work there directly).

## Verification constraints

The sandbox has no browser: no live dev server URL, no literal
screenshots. Every milestone therefore ships two things:

1. Real, downloadable project files, run locally with `npm run dev`
2. A matching static HTML/CSS preview using the same design tokens, for
   immediate visual review without needing to run anything

`npx tsc --noEmit` runs clean in-sandbox and is the real correctness
signal. `npm run build` will fail in-sandbox specifically on the Google
Fonts network fetch (blocked from this environment) — that is an
environment limitation, not a code defect, and resolves on a machine with
normal internet access.
